# What v0.1.0 leaves out

v0.1.0 is the first of four planned milestones, **Contain**: virtual keys you can cap, limit and kill, in front of real credentials that stay sealed. The later milestones add detection, a dashboard and realtime, and **none of what they will add is in this release**. This page lists what is missing, so that you don't look for it, and says what to do in its place.

If something here matters to you more than the rest of kman does, wait for the release that has it.

## A key leaked

**What's missing:** key rotation (replacing a key's secret while keeping its id) and any automatic response.

**Do this:** make a new key, give it to the app, and revoke the old one. The old key stops working at its next request.

```sh
kman key create my-app-2 --upstream openai      # prints the new key once
# …give the app the new key, then:
kman key revoke my-app
```

The new key has a new id, so its spend starts from zero: the old key's spend history stays with the old key (`kman key list --json` still shows it). If you don't know which key leaked, `kman key list` and `kman audit` show what exists and who changed what.

To pause a key while you find out, `kman key disable my-app`; `kman key enable my-app` brings it back.

## A real credential leaked

**What's missing:** a command that handles the compromise of an upstream credential for you.

**Do this, in this order:**

1. **At the provider**, revoke the leaked real key and make a new one. That is what stops the damage; nothing kman does reaches the provider.
2. Give kman the new secret. Every virtual key on the credential keeps working, with no restart, and the old secret is wiped from kman's memory:

   ```sh
   kman credential update openai       # asks for the new secret, without echo
   ```
3. If the leak also took virtual keys, revoke and replace them as above.

If the **master key** leaked, the data directory is readable by whoever holds a copy of it: see [Replace the master key](operator-guide/upgrade.md#replace-the-master-key), and rotate every credential at its provider as well.

## Looking for leaked keys

**What's missing:** the scan and exposure commands, which would search your files and logs for kman keys.

**Do this:** a virtual key has a fixed shape, and this pattern (published, so scanners can copy it) matches one, and a child key with its `ek_` prefix:

```
\b(?:ek_)?kmn_[0-9A-Za-z]{8}_[0-9A-Za-z]{49}\b
```

```sh
grep -rEn '(ek_)?kmn_[0-9A-Za-z]{8}_[0-9A-Za-z]{49}' path/to/repo
```

(That `grep` form leaves out the `\b` word boundaries, which not every `grep` has; expect an occasional longer match.) The eight characters after `kmn_` are the key's id, so a match tells you which key to revoke: `kman key show <id>`. Admin tokens start with `kma_` and are not matched.

## Address locks

**What's missing:** limiting a key to the addresses or countries it may be used from (`address_not_allowed` exists as a name, and nothing returns it).

**Do this:** restrict by network. Leave the proxy on loopback or a private interface, and allow only your own machines to reach it with a firewall or the reverse proxy in front ([TLS and reverse proxies](operator-guide/tls.md)).

## Alerts, soft budgets, events and metrics

**What's missing:** anything that tells you something happened: alert channels, soft budgets that warn at 50 or 80 percent, a live event stream, and following the audit log live. (Events, hourly usage and Prometheus metrics are in: [Events and metrics](operator-guide/metrics.md).)

**Do this:**

- **Hard caps are the limit that works.** A key's `daily_cap_micro` and `monthly_cap_micro` refuse requests past them ([Keys, policy and spend](policy.md)). The `soft_budget_defaults` setting exists and `kman settings` stores it, but **nothing in v0.1.0 acts on it**.
- **Scrape the metrics.** `/metrics` on the admin listener (with an admin token), or on `metrics_listen` if you set it, carries requests, refusals, tokens, cost and `kman_price_data_age_seconds` per key, for Prometheus to alert on ([Events and metrics](operator-guide/metrics.md)).
- **Poll the spend.** `kman key list --json` carries each key's spend for today and this month, and `kman key show <name>` prints it. Run it from cron and alert on what you care about.
- **Read the log.** `kman serve` logs to standard error: it starts and stops, and failures: an upstream that could not be reached, a stream that broke, a redirect that was blocked, an unreadable policy, each with the key id and the upstream name, never a path or query string. It does **not** log every request, and no secret is in it.
- **The audit log** records every change made through the admin API, with who made it: `kman audit` lists the newest entries, `kman audit export` writes them all as JSON Lines.

## Backup, restore and prune

**What's missing:** commands to take a consistent backup while kman runs, to restore one, and to prune old data.

**Do this:** [Back up the data](operator-guide/upgrade.md#back-up-the-data): stop kman, copy the data directory, and keep the master key apart from it. kman keeps every audit entry and daily spend row it writes; nothing in v0.1.0 prunes them, and `kman.yaml` has no retention setting.

## Everything else that isn't here

- **A dashboard.** The CLI and the [admin API](admin-api/README.md) are the whole interface.
- **A demo mode, canary keys, detection and incidents.** Nothing watches traffic for the patterns of a leaked key, and no key is a tripwire.
- **Realtime.** WebSocket and realtime sessions, and the short-lived child keys (`ek_…`) for browsers, are M4. A child key is refused as `invalid_key`.
- **GeoIP, retention and update checks.** kman never checks for a new version: watch the [releases](https://github.com/kirank55/kman/releases). It makes no network call you didn't configure.
- **The Windows and macOS review.** The [security review](security-review-v0.1.0.md) ran on Linux.

When any of these ships it is in the [changelog](../CHANGELOG.md) and this page changes.
