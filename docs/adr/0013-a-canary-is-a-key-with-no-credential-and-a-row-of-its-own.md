# A canary is a key with no credential and a row of its own, and its first use alerts at once

A canary key is a tripwire: an operator plants a key where a leak would find it, and any use of it is a leak. The gateway already recognised one (a key with no credential answers `invalid_key` like any bad key and sends its use down the priority lane); what was missing was any way to make, list and re-arm one (#87). This ADR records how a canary is represented, what an ignore list is, what a reset does, how a repeated use alerts, and what an operator and a thief each see.

- **A canary is a `virtual_keys` row of kind `canary` with no credential, and a `canaries` row.** The key row is what the request path reads: it has the key id and the hash of the secret, so the gateway finds the key, checks the secret, and refuses with `invalid_key`. The `canaries` row (migration `0002`) is what a canary has beyond that: where it was planted, its ignore list, when it was armed, whether it has fired (`fired_at`, the first use since it was armed, NULL while armed), when it last fired, how many uses were counted, and what the last use looked like (address, country, ASN, its organisation, client). Nothing in the token says it is a canary (ADR 0001): a canary's secret is minted by the same function as any virtual key's, and its key id is eight random base62 characters.
- **A canary has no expiry.** The gateway checks expiry before it checks for a credential, so an expired canary would answer `key_expired` and raise nothing: a tripwire that goes quiet on a date is worse than none. SPEC §4 says every key expires; a canary is the one exception, and it is retired by revoking it, not by waiting.
- **It is retired with `kman key revoke`, and no other key command touches it.** `key disable` would make its use a "disabled key" alert (high) instead of a canary's (critical); `key enable`, `key rotate` and `key update` have nothing to do for a key that forwards nothing. They answer with a conflict that points at `kman canary`. A revoked canary answers `key_revoked` and raises nothing, and `kman canary list` shows it as revoked.
- **`kman key list` does not list canaries, and `kman exposure` does not count them.** A canary is not a key that could be abused: it has no address lock, never expires and is never used, which are the three things exposure looks for, so counting it would make every install's exposure report wrong by design. `kman key list`, the status summary and the terminal dashboard read the same list, so one rule covers them: the list holds the keys that work, and `kman canary list` holds the canaries. A canary is still found by its name or key id, `kman key show` says it is a canary, and `kman key revoke` takes it.
- **What an operator plants is a snippet that holds the key and nothing else.** `kman canary create --format env|mcp|shell|ci` prints, once, the lines to plant: `OPENAI_API_KEY=kmn_…` for a `.env` file, `export OPENAI_API_KEY=kmn_…` for a shell profile, an `mcpServers` block with an `env` object for an MCP client's config, and `gh secret set OPENAI_API_KEY --body kmn_…` for CI. `--var` names another variable, and `--base-url` adds the matching base URL (`OPENAI_BASE_URL`), because a canary fires only when someone sends it to kman, and a thief who finds the key alone does not know where kman is. The snippet carries neither the canary's name, nor where it is planted, nor its tags, nor the word canary: whatever the thief reads must not say what it is. The secret and the snippet are shown once, on creation, and never again; they are not in the audit log, the list or an alert.
- **An ignore list is the addresses whose use does not fire the canary.** It is a list of addresses and CIDR networks, at most 100, none wider than an IPv4 /16 or an IPv6 /32 (a list that held every address would silence the canary, which is the one thing it must not do). It is for the operator's own scanners, such as a secret scanner that sweeps the repository the canary is planted in. A use from an address on it is still an event, so it still shows in `kman events` and in the key's places, but it does not fire the canary, count as a use, or raise an alert. **Nothing else silences a canary.** A known source ([the glossary](../../GLOSSARY.md), #88) is a range an operator has said is legitimate for the baseline rules, and it never applies to a canary: an address a canary was used from before, one the install has seen a thousand times, or a known source, all still alert. The ignore list is the one list the operator writes for a canary, and it is per canary, so one canary's scanner does not blind another.
- **A canary alerts on its first use after it was armed, and then once per window.** The use is recorded on the canary's row in the same transaction that queues the alert, so the state and the alert are never apart, and a restart loses neither. The first use after it was made or reset always alerts, even inside the throttle window, since a reset is the operator saying "tell me again". After that the canary is fired: more uses are counted (`fires`, `last_fired_at`, and what the last one looked like) and alert at most once per throttle window (ten minutes), each such alert saying how many uses it held back. A leaked canary is a stream of requests, and an operator needs the first alert and a count, not the stream; the bound is one alert per canary per window, and the throttle's memory is bounded (4,096 keys).
- **A reset arms it again and keeps its history.** `kman canary reset <canary>` clears `fired_at` and sets `armed_at`; when it last fired, how many uses were counted and what the last one looked like stay, so the list still says "last fired" after a reset. Resetting an armed canary changes nothing and writes no audit entry, and a revoked canary cannot be reset.
- **A canary alert says where it was planted and where the request came from.** Its evidence is where it was planted, the address, the country, the ASN with its organisation, the client (ADR 0012), and the method; never the path or anything else the request said. The address is personal data (ADR 0010), but an alert goes to the operator's own channels to say who used a tripwire, which is the point of one, so it is in the alert. The country, the AS and its label come from the operator's GeoIP databases and are cleaned of control characters and cut to 64 characters before they go to a channel.
- **The admin API gives out what a canary saw, less the address.** `GET /admin/v1/canaries` and a single canary say whether it fired and when, how many uses were counted, and the country, ASN, organisation and client of the last use, and withhold its address (`address_withheld`) unless `expose_client_addresses` is on. The address of the last use is kept on the canary's row, one address that each use replaces, and is not pruned by retention.
- **The deadline is a gate, and it is its own job in CI.** `TestCanaryDeadlineGate` (in `e2e`) runs the real binary with 256 clients sending requests through it at once and one alert channel that never answers, and requires a canary's alert and a disabled key's to reach the healthy channel within 5 seconds. It is an e2e test because it is about real queues, a real SQLite and a real clock, and the clock seam (SPEC §17) keeps wall-clock waits out of the unit tests under `internal/`; the pipeline's logic under the same load is tested there on a fake clock, where the alerts must arrive with no time having passed. The e2e gate runs in `go test` and as a job of its own that the required job waits for (SPEC §17, M2).
- **Migration `0002` grew, and a database from an earlier build of it is refused.** Until `v0.2.0` is tagged, M2 tickets add to `0002` (SPEC §14), so a data directory that ran an earlier build of it is at schema 2 and lacks the `canaries` table. `Open` checks that a database at an unreleased version has what that version now creates and, if not, refuses with "rebuild the data directory (unreleased migration changed)", instead of failing on the first query that needs the table. When a release is tagged its version comes off the list in `internal/store/migrate.go` and a later ticket appends a migration of its own.

## Considered options

- **A canary as a flag on an ordinary key, with a credential.** Rejected. A key with a credential would forward a request to the provider with kman's real credential, so a canary's use would cost money and leak a real call. A canary has no credential so that it cannot forward anything.
- **Ignoring the expiry check for a canary in the gateway, so a canary could have one.** Rejected. It adds a branch to the hot path to keep a field no operator needs: a canary that stops working on a date is the thing to avoid, and revoking is how an operator ends one.
- **Putting the canary's state in `virtual_keys`.** Rejected. `virtual_keys` is the row the request path reads and every key command moves, and its columns are shared by keys that have no ignore list or fired state. A row of its own keeps the key table what it was and lets a later ticket (incidents, #88) change canary state without touching it.
- **Alerting on every use of a fired canary.** Rejected. A leaked canary is hammered by whoever holds it, and each alert would be a message to the operator's phone. One per window with a count says the same thing.
- **Alerting on the first use only, until a reset.** Rejected. An operator who has seen the first alert and not reset it would never hear that the leak is still in use, or that it moved to a new address. One alert per window keeps saying so, at a bounded rate.
- **Letting a known source or a familiar address silence a canary.** Rejected. A canary has no legitimate user; any use, from anywhere, is the event. The only address that may be ignored is one the operator names for this canary.
- **Hiding the canary from `kman key list` only in the CLI.** Rejected. The status summary and the terminal dashboard read the same admin API list, and would each need the same rule. One rule in the admin service covers them all.
- **A disguised canary, a fake `sk-proj-…` key.** Rejected by ADR 0001: a thief would use it against the provider, where kman never sees it.

## Consequences

- SPEC §4 and §12, the glossary, the changelog, the operator guide and the threat model describe the canary as built. `kman canary create|list|show|update|reset` and `/admin/v1/canaries` are in the generated CLI and API references.
- A canary's secret is stored as a hash in `key_secrets` like any key's, and the secret-leak sweep covers it: the secret is shown once, and appears in no list, alert, audit entry or log.
- An operator's note on where a canary is planted is in the audit log and in alerts. It is the operator's own text and can say anything; it is limited to 200 characters with no control characters.
- A thief who sends the canary to kman is told `invalid_key`, as for any key, and an operator can tell a canary from a bad key only by the alert. A thief who sends it with the wrong secret, or the key id alone, raises nothing: the secret must be right, which only holding the snippet gives.
- An existing database from before this change, at schema 0002, does not have the table: a developer who ran an earlier build of it needs a fresh data directory, and `Open` says so. No release has had it.
- Incidents (#88) will open one per canary use; the canary's row is where its state lives until then, and the alert is what it raises now.
