# An event records the calling client, reduced to a product and a major version

kman's events hold "what happened and never what was said": no content, no query string, no secret, and until now no header at all (SPEC §9). To tell a leaked key from the app it belongs to, an operator needs one more fact about a request, and a header is the only place it is: **what is calling**. A key used by `openai-python/3` from its usual network, and then by `curl/8` from a new one, is the clearest sign of a leak there is, and it is the first thing a location rule will compare (#83). This ADR makes the `User-Agent` the one exception to the rule that an event keeps no header, and keeps the exception as small as it can be.

- **What is kept: a client.** The `User-Agent`'s first product and its major version, in lower case: `openai-python/3`, `anthropic-js/1`, `curl/8`, `python-requests/2`, `go-http-client/1`. An SDK that names itself `Vendor/Language 1.2.3`, as the official OpenAI and Anthropic SDKs do (`OpenAI/Python 3.49.0`, `Anthropic/JS 1.8.0`), is read as `vendor-language/1`. A product that is not one kman knows is kept the same way, as its first token and its major version, with no list of recognised agents to keep up to date: an unrecognised agent is its first product token, at most 32 bytes long in all. No `User-Agent` is the client `none`. A `User-Agent` that holds no product kman is willing to keep is the client `unknown`.
- **What is dropped: everything else.** The minor, patch and build numbers (version noise: `curl/8.5.0` and `curl/8.6.0` are one client), the comment in parentheses, every product after the first, and the header's own text. The raw header is never stored, logged, put in a metric or sent in an alert; only the reduction is.
- **What an app put there that it should not have is dropped by construction, not by looking for it.** Only a word of letters, digits, `_` and `-` that starts with a letter, followed by a number of up to four digits, survives. The first word has to be a whole product name: if it is followed by `@`, `:`, `.` or anything else that is not a separator, it is not a name but an email, a host name, a URL, an address or a path, and the client is `unknown`, not a shortened version of it. A name that holds `kmn_` in any case (a virtual key, and a child key's `ek_kmn_`) is `unknown`, and so is any name of twenty characters or more with a digit in it, which is what a random token looks like (`sk-proj-...`, a hex digest), and any name with more than one run of digits or more than three digits, which is what a host label (`ip-10-0-3-7`, `node-0042`) or a short token (`a1b2c3`) looks like; a product's name holds a digit or a short number at most (`urllib3`, `aws-sdk-go-v2`). A first word that fills all 256 bytes read is `unknown` too, since what follows it cannot be seen. Control characters, non-ASCII bytes and anything past the first 256 bytes are never read. What cannot be told from a product, such as a person's first name as the whole header, can survive; it is bounded to one word of 32 bytes and no more.
- **The reduction is a pure function, `events.ClientOf`**, the one place a `User-Agent` is read. It is table-tested against the `User-Agent` of every SDK pinned in `e2e/testdata/sdk` (a test fails when a pin moves, until the table is brought up to date), curl and hostile inputs, fuzzed to keep its output a bounded product-and-version shape that never holds a key, and run in the e2e suite against the real SDKs.
- **It is stored in `events.client` and in `baseline_places` as `kind = client`.** Places are kept forever and counted like countries, ASNs and networks, so `kman key places` says which clients have used a key and when each was first and last seen, and a key keeps at most 1,000 of them (the rest counted as `other`), so a client that varies its `User-Agent` cannot grow the table. Both are part of migration `0002`, which has not been released, so it is extended rather than followed by a migration `0003`. Events stored before it have no client (NULL), which is not the client `none`, and make no client place.
- **It is shown always.** A client names a program, not a person or an office, so unlike a client address or a network it is not withheld by `expose_client_addresses` ([ADR 0010](0010-client-addresses-are-opt-in-on-the-admin-api.md)). The admin API gives out `client` on every event and `kind = client` places, `kman events` has a `CLIENT` column (the address column, which was called `CLIENT`, is now `ADDRESS`), and the key view of `kman tui` lists clients with the other places.
- **It is read where the event is made.** The gateway reduces the header once, when the request ends and its event is emitted, so no stage of the pipeline waits for it and it cannot refuse a request. It reads 256 bytes at most, so a flood of made-up keys, which `BenchmarkBadKey` stands for, costs next to nothing more. An event for a request that proved no key carries its client too, so probing can be told apart by what it comes from. Such a client is not a place, since there is no key to attach it to.

## Considered options

- **Keep no header, as before.** Rejected. Without the caller, "where from" is half the answer, and the new-client rule of #83 has nothing to compare.
- **Store the whole `User-Agent`.** Rejected. It is app-controlled free text that can hold keys, tokens, host names, email addresses and users' names, and it would put all of it in the database, the backups, the event feed and the alerts. It also varies by minor version, build and operating system, so a baseline of it would never settle.
- **Keep the whole product token and version, without a major version cap, or add the operating system.** Rejected. Every extra field is more noise and more of what an app wrote, and the major version is what tells a leak from an upgrade: a new minor release is not news, a new product is.
- **A list of known agents, and `other` for the rest.** Rejected. It would need keeping up to date, and a leak from an unfamiliar tool (the first thing to be told apart) would read as `other`. The first token is the same for known agents and costs no list.
- **Scrub the keys, tokens and addresses out of the header and keep the rest.** Rejected. A scrubber only removes what it knows to look for. Keeping only what is a product name and a number is the safer way round: whatever is not recognised is cut.

## Consequences

- The `User-Agent` is now the one header kman's events hold, and only reduced. SPEC §9 and the threat model say so; the secret-leak sweep (`e2e/secrets_test.go`) plants a `User-Agent` with a sentinel, an address and a key in it, and finds none of them in kman's output, files or logs.
- A client is an app's own claim, as easy to change as the header: a holder of a leaked key can say it is `openai-python/3`. It is a signal for an operator and for later rules, not proof of who is calling, and kman does not treat it as authentication.
- Two clients on one machine, such as two services using the same SDK, are one client. A client names a product, not an app.
- An existing database from before this change, at schema 0002, does not have the column: migration `0002` was changed in place, as #83 says, so a developer who ran an earlier build of it needs a fresh data directory. No release has had it.
- Later tickets build on it: the location rules that compare a new client (#89, #91) read `kind = client` places, and an alert may name the client of the request it is about.
