# Changelog

All notable changes to kman are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and kman uses
[semantic versioning](https://semver.org/). A release's section, headed
`## [<version>]`, becomes its GitHub release notes.

## [Unreleased]

### Added

- `kman scan <path>...` finds kman keys in files and standard input, offline. It matches the published pattern, confirms each match by its checksum, reports a child key at `low` severity as "child key (short-lived)", never prints a secret, names the key id to revoke, and exits 3 when it finds one. `--json` is the report.
- `kman exposure [--strict]` lists the keys that work now and are open to every address, never expire, or have forwarded nothing for 30 days, each with the command that fixes it. `--strict` exits 3 on findings. `GET /admin/v1/exposure` is its admin API route.
- Address locks. A key's policy takes `allowed_cidrs` (networks, or bare addresses) and `allowed_countries` (ISO 3166-1 codes); a request from anywhere else is refused with 403 `address_not_allowed` before its body is read. With both, the address must satisfy both. The client address is the connection's, or `X-Forwarded-For` only through `trusted_proxies`.
- `geoip` in `kman.yaml`: `country_db` and `asn_db`, paths to `.mmdb` files, read at startup. `kman geoip update` downloads DB-IP Lite (CC BY 4.0) there, and is the only place kman contacts DB-IP; `--source` takes a mirror. A database you supply works as well.
- A country lock with no country database is refused when the policy is set, with a message saying what to do; kman refuses to start with country-locked keys and no database, or with a named database that cannot be opened. An address no database knows fails a country lock.
- Alerts. `kman channel add|list|test|rm` manages Slack and signed-webhook channels, each with a `min_severity` (default medium) and a toggle for spend and lifecycle warnings (default on). Alerts go through a persisted outbox with retries and backoff, so they survive a restart, and each channel has a delivery worker of its own, so a channel that hangs neither drops nor delays another's alerts. The audit log is an alert producer, and so is the use of a disabled key or a canary, on the priority lane. An alert holds the key's name and id, the severity, evidence and copy-paste commands, never a secret or request content. A webhook carries `X-Kman-Signature`, an HMAC-SHA256 under a signing secret shown once. `dashboard.url` in `kman.yaml` is optional. The admin API has `/admin/v1/channels`. See [Alerts](docs/operator-guide/alerts.md).
- `kman key rotate <key> [--grace <duration>]` replaces a key's secret and keeps the key: its id, spend, policy and audit history stay (ADR 0002). The new secret is printed once. During a grace (up to 30 days) both secrets work; a second rotation inside a grace ends the older secret at once, so a key holds at most two. When the grace ends, the old secret becomes a retired secret: its hash is kept 30 days and never authenticates. A rotation that fails leaves the key as it was. The admin API has `POST /admin/v1/keys/{id}/rotate`.
- `kman credential compromise <credential>` replaces a leaked credential's secret and rotates every virtual key on it that is not revoked, with no grace, in one transaction, then lists the apps that need new keys with their new secrets. The admin API has `POST /admin/v1/credentials/{ref}/compromise`.
- `kman backup <file>` writes a consistent copy of the database while kman runs (a `VACUUM INTO`, streamed from the server, so the file is made on the machine you run it on, `0600`, and is never overwritten). It holds ciphertext only: it opens only with the master key, which is backed up separately. Each backup is audited. The admin API has `POST /admin/v1/backup`.
- `kman restore <file>` replaces the database with a backup, with the server stopped and the master key the backup was made under; both are checked before anything changes. The database it replaces is kept as `kman.db.before-restore`, and the restore is audited in the restored database. It needs no migration: the schema is unchanged.
- Retention: kman prunes events after 30 days, hourly usage after 400 days and delivered alerts 30 days after delivery, at startup and daily; daily spend, incidents and the audit log are kept forever. `retention: keep_everything` in `kman.yaml` turns pruning off. A pass that deletes something is audited as `system:retention`.
- `kman prune --before <date> [--audit-log]` deletes what is older than a date and is always audited. `--audit-log` also prunes the audit log, the one thing that ever deletes from it, through the guard its trigger allows; the record of the prune stays. The admin API has `POST /admin/v1/prune`.
- `kman version --check` asks the GitHub releases API once, when run, whether a newer release exists. `update_check: true` in `kman.yaml` (off by default) makes `kman serve` check daily; the answer shows in plain `kman`, in `GET /admin/v1/update` and as `kman_update_available`. Nothing else in kman contacts GitHub (ADR 0008).


## [0.1.0] - 2026-11-11

The first release: put real API keys behind kman and kill a leak. kman is a key manager and proxy for LLM API keys. You keep the real keys in kman, hand apps virtual keys that cap spend and expire, and turn one off the moment it leaks.

### Added

- `kman init` sets up an install without asking anything: `kman.yaml` and a `0600` master key in the config directory, the data directory, and the `owner` admin token, printed once and saved to a `0600` credentials file. `--data-dir`, `--key-source file|systemd-creds|passphrase|env` and `--no-save-token`. In a container it needs a key from outside and never saves the token.
- `kman rekey` replaces the master key and the data key while the server is stopped: a new data key, wrapped under a new master key, with every credential and alert channel resealed in one transaction, and an audit entry. A rekey that fails leaves the database as it was, and it refuses to run beside a running server. kman makes the new key for the file and passphrase sources; `--new-key-file` takes one from `kman keygen`, and `--new-key-source` moves an install to another key source.
- `kman serve` binds the proxy to `127.0.0.1:8080` and the admin API to `127.0.0.1:8081` (or a `0600` Unix socket), with optional TLS per listener. It refuses a master key inside the data directory, an empty data directory, and plain HTTP on an admin address that is not loopback, and it shuts down cleanly on SIGINT and SIGTERM.
- The admin API, `/admin/v1`: the one way to change a running kman. Every change is one store transaction with an audit entry naming its actor, the admin token's name. Requests authenticate with an admin token as a bearer token, never a cookie. Its OpenAPI 3.1 document is generated from the Go types, served at `/admin/v1/openapi.json`, and committed as `docs/admin-api/openapi.json`.
- Named admin tokens: `kman admin-token create|list|rotate|revoke`. A revoked token is refused from its next request on, and the last live token cannot be revoked. Rotating the CLI's own token saves the new secret to the credentials file.
- `kman settings get|set` for `max_key_lifetime` (365d), `default_key_ttl` (90d), `spend_timezone` (UTC) and `soft_budget_defaults` (50,80,100), each change audited.
- `kman audit` lists the newest audit entries with their actor; `kman audit export` writes every entry as JSON Lines.
- `kman login --admin-url <url>` checks a token with the server and saves both to the credentials file; `kman logout` removes it. `KMAN_ADMIN_TOKEN` and `KMAN_ADMIN_URL` override the file.
- Every read command takes `--json`. Exit codes are 0 OK, 1 error (usage errors included), 3 findings.
- `kman init --proxy-listen`, `--admin-listen` and `--allow-plain-http`, each also read from `KMAN_PROXY_LISTEN`, `KMAN_ADMIN_LISTEN` and `KMAN_ALLOW_PLAIN_HTTP`. init now refuses, before writing anything, a config that serve would refuse.
- `kman upstream add|list|show|update|rm|sync`: an upstream comes from one of 21 built-in presets (`kman upstream add openai --preset openai`) or is built with flags, with header or Basic auth. A preset is copied once, recording its version; an upgrade never changes an existing upstream, and `kman upstream sync` shows the difference from a newer preset and applies it after a confirmation.
- `kman credential add|update|rm`: credentials are sealed under the data key, never shown after entry, and audited. A secret is asked for without echo, piped, or read from the variable `--credential-env` names, and is never an argument. `upstream add` takes the first credential in the same step.
- Deleting an upstream or a credential is refused while a virtual key that is not revoked depends on it. Names are unique among items not deleted.
- `kman serve` holds the upstreams, credentials and virtual keys in a lock-free snapshot, rebuilt at startup and updated by every admin command after it commits, and refuses to start with a credential it cannot decrypt.
- `kman key create|list|show|update`: a virtual key on an upstream, with an optional name, a note and tags. Its secret is shown once, at creation, and only its hash is stored. The CLI takes a name or a key id; the admin API, `/admin/v1/keys`, uses key ids.
- `kman key disable|enable|revoke <name or key id>`: each is audited and takes effect on the key's next request, with no restart: a disabled key gets 403 `key_disabled`, a revoked one 401 `key_revoked`, and a key past its expiry 401 `key_expired`. A revoked key is final: it cannot be enabled, and its name can be used again. Enabling a key does not extend its expiry. No key may be created or extended past the maximum key lifetime, counted from its creation, and `never` is refused.
- The proxy listener serves: an app sends a virtual key, in place of an upstream's key, and kman forwards the request with the real credential. A token's checksum is checked before any lookup. Inbound auth, hop-by-hop and forwarding headers stop at kman, and kman adds none of its own. Paths and query strings pass through unchanged and are never logged, and responses, streams included, pass back as they arrive.
- kman uses no proxy from its environment to reach an upstream, and follows no redirect. A redirect within the upstream is rewritten to stay on kman, and a redirect anywhere else is a 502, so an app never carries its virtual key off kman. Request bodies over 32 MiB are refused with a 413. TRACE, CONNECT and `OPTIONS *` are refused with a 403.
- The OpenAI and Anthropic profiles: chat, responses, messages, completions and embeddings work through kman from the official SDKs, with and without streaming. kman reads each response's usage as it passes (tokens by kind, the model, the service tier, server-tool calls and any cost the provider reports) without holding the stream back.
- OpenAI-style chat and completion streams are asked for their usage with `stream_options.include_usage`, on upstreams with `inject_usage`, overriding an app's own `false`. An app that didn't ask gets one more chunk at the end of the stream, with an empty `choices`. Requests to OpenAI and Anthropic profile upstreams go out with `Accept-Encoding: identity`, so apps get those responses uncompressed: a compressed one would hide its usage.
- Errors from the proxy are OpenAI-shaped JSON with an `X-Kman-Error` header holding the code: `invalid_key`, `key_expired`, `key_revoked`, `key_disabled`, `path_not_allowed`, `model_not_allowed`, `unmetered_request`, `request_too_large`, `rate_limited` and `upstream_unavailable` so far.
- A new key expires after `default_key_ttl`, or the `--ttl` given. No key is created or extended past `max_key_lifetime`, counted from its creation, and `never` is refused.
- Each key has a policy, a versioned JSON value that starts empty and is edited with `kman key update --policy`, audited. A field kman does not know is refused.
- A key's policy takes `allowed_paths` (rules such as `POST /v1/chat/completions`, where `*` is one segment and a last `**` is the rest), `allowed_models` (exact ids, or an id ending in `*` as a prefix) and `rpm_limit`, set with `kman key update --policy`. An upstream's own path list now holds every key on it. A key's `allowed_paths` replaces its upstream's list for that key, so it can narrow it, or, with no model allowlist, add a route the upstream's list leaves out. A path with a `..` or `.` segment, an empty segment, or an encoded slash or backslash matches nothing, and is refused with `path_not_allowed` instead of being forwarded as sent. A key with a model allowlist refuses a request kman cannot read a model from (no body, not JSON, a repeated or non-text `model`) as `unmetered_request`.
- A key over its `rpm_limit` gets a 429 `rate_limited` with `Retry-After`. An address that presents more than 30 invalid keys in a minute is refused with the same 429, good keys included, until the minute passes; revoked, expired and disabled keys are not counted. Limiter memory is bounded (10,000 keys and 10,000 addresses, least recently used out first), and an IPv6 network of 64 bits counts as one address.
- `trusted_proxies` in `kman.yaml`: addresses or networks of reverse proxies in front of the proxy listener, whose `X-Forwarded-For` kman believes, read from its right. With none, a request's address is its connection's.
- Plain `kman` is now a status summary: where the install stands (not initialised, not running, no upstream, no key, ready), the next command, any upstream with a newer preset, how old the binary is (its build date, which is its commit's date) and how old the price data is.
- Best-effort packages: a `.deb` and an `.rpm` for amd64 and arm64 with a sandboxed `kman.service` (`DynamicUser=yes`, `StateDirectory=kman`, `ConfigurationDirectory=kman`, the master key through `LoadCredentialEncrypted=`), and a Homebrew formula in `kirank55/homebrew-tap` for stable releases (`brew install kirank55/tap/kman`). See `docs/operator-guide/systemd.md`.
- A Compose example, `examples/compose/compose.yaml`: the key as a secret, the data on a volume, a read-only root filesystem, and both listeners published on host loopback only. See `docs/operator-guide/docker.md`.
- `kman price list` shows the built-in price table and how old it is, and plain `kman` shows the age too. Past 60 days both say `price data is N days old, upgrade kman`. Age never changes what kman enforces.
- `kman price set|rm|import` set price overrides, install-wide or per upstream, each with an input price, an output price and a max output, so an operator can price a model kman doesn't know, or correct a price, without waiting for a release. An override wins until removed, and `kman price list` marks those that hide a built-in entry. Every change is audited. See `docs/price-data.md`.
- `--price-multiplier` on `kman upstream add` and `update` scales built-in prices and install-wide overrides on one upstream, for a regional uplift. It defaults to 1.
- The price table: generated from LiteLLM, cross-checked against genai-prices v2 and models.dev, keeping the conservative value, and embedded in the binary. It models long-context tiers, prices by modality, per-minute voice prices, per-call server-tool fees and service tiers, with DeepSeek at its peak price. Model ids match exactly. kman never fetches price data at runtime. See `docs/price-data.md`.
- Spend and caps. Every key on an OpenAI or Anthropic profile upstream has spend for the day and the month, capped or not, kept in memory, flushed to the store as increments every 5 s and on shutdown, and read back at startup. A key's policy takes `daily_cap_micro` and `monthly_cap_micro` (microdollars, for example `kman key update my-app --policy '{"daily_cap_micro":5000000}'`). A request is reserved for before it is forwarded (its bytes ÷ 4 at the input price, plus its output allowance at the output price) and refused with `spend_cap_reached` if committed spend, open reservations and the new one would pass a cap; a key never goes over by more than one request. Periods begin at 00:00 in `spend_timezone`, which is read when kman starts.
- A response is charged what it reports, at the model, tier and cost it reports, whatever its status. A non-2xx with no usage costs nothing. A stream that breaks, an app that leaves, and a 2xx that reports no usage are charged the whole reservation, marked estimated (except the free routes `count_tokens`, `input_tokens` and `moderations`). Capped keys fail closed with `store_unavailable` once spend has failed to reach the store for 60 s.
- A key with a cap or a model allowlist refuses a request kman can't meter, with `unmetered_request` (no top-level `model`, a body that isn't JSON, or a generic upstream) or `unknown_model_price`, which names the model, the upstream and the `kman price set` command. That includes `GET /v1/models`. Other keys forward such requests and show them as unmetered, never as $0.
- `kman key show` prints each key's spend today and this month beside its caps, and `key show --json`, `key list --json` and `GET /admin/v1/keys` carry the same `spend`.
- Documentation: a README and a [quickstart](docs/quickstart.md) that CI runs line for line on Linux and macOS; an [operator guide](docs/operator-guide/README.md) (install per platform, with macOS quarantine and the Windows SmartScreen warning, key sources, systemd, Docker and Compose, TLS behind a reverse proxy, upgrade, the `kman.db.pre-<NNNN>` copies and what to do about old copies after a rekey); [keys, policy and spend](docs/policy.md); [SDK snippets](docs/sdks.md) that CI runs through the real kman with the pinned official SDKs, and a table of each preset's key variable and base URL; [what v0.1.0 leaves out](docs/v0.1.0-scope.md) and what to do meanwhile; [THREAT-MODEL.md](THREAT-MODEL.md) and [SECURITY.md](SECURITY.md).
- Every release archive carries `NOTICE-price-data`, the licences of the datasets the embedded price table is generated from. Which test checks each of M1's done criteria is in [docs/v0.1.0-done.md](docs/v0.1.0-done.md).
- A [CLI reference](docs/cli.md), generated from each command's help, and an [admin API reference](docs/admin-api/README.md), generated from the OpenAPI document. CI fails if either is stale, if a doc names a command or a flag kman does not have, or if a link in the docs does not resolve.

### Security

- The proxy no longer lets a request hold a connection or memory by sending its body slowly, or by promising a body it never sends: a body that stops arriving for 30 s, or takes over 5 minutes, ends the connection; request bodies held in memory are capped across all requests (512 MiB, then 429 `rate_limited`); a refused request no longer waits for the rest of its body; listeners close idle connections after 2 minutes and limit a request head to 64 KiB. Found by the v0.1.0 security review ([docs/security-review-v0.1.0.md](docs/security-review-v0.1.0.md)).
- `kman rekey`'s report no longer points at a command this release does not ship.
